# OpsDemyst AWS Cost Analyzer

**Open-source AWS cost analysis and recommendation engine built around AWS Cost and Usage Report (CUR) data.**

OpsDemyst AWS Cost Analyzer helps you analyze AWS billing data and identify practical cost-optimization opportunities using a deterministic, rules-based recommendation engine.

It is designed to be **self-hosted, transparent, and easy to run locally with Docker**.

---

## What It Does

The application accepts AWS Cost and Usage Report (CUR) data, processes the billing information, and generates cost-optimization recommendations based on predefined analysis rules.

The current open-source edition focuses on a small set of practical AWS cost signals:

1. **Low EC2 commitment coverage**
2. **EBS volumes using gp2 instead of gp3**
3. **High data transfer costs**
4. **NAT Gateway spend**
5. **Cost spike detection**

The recommendations are generated from the available billing data and configured rules. They are intended to help users investigate potential optimization opportunities rather than automatically modify AWS resources.

---

## Why OpsDemyst AWS Cost Analyzer?

AWS billing data can contain a large amount of information, while the actual cost-optimization opportunities may be difficult to identify quickly.

This project aims to make that analysis more accessible by providing:

* A self-hosted application
* Docker-based local deployment
* AWS CUR data processing
* Deterministic cost-analysis rules
* Action-oriented recommendations
* A simple dashboard
* PostgreSQL-based persistence
* No requirement to provide the application with direct access to your AWS account

The project is intended to provide a practical starting point for understanding AWS cost patterns and potential optimization opportunities.

---

## Key Principles

OpsDemyst AWS Cost Analyzer is built around a few simple principles:

- **Practical** — focus on cost signals that can lead to concrete investigation.
- **Transparent** — recommendations are generated by explicit analysis rules.
- **Self-hosted** — users can run the application in their own environment.
- **Data-driven** — analysis is based on AWS billing and usage data.
- **Non-destructive** — the analyzer identifies opportunities but does not automatically modify AWS resources.
- **Incremental** — capabilities are added gradually based on real-world use and feedback.

## Quick Start

Clone the repository:

```bash
git clone <repository-url>
cd opsdemyst-aws-cost-analyzer
```

Create your local environment file:

```bash
cp .env.example .env
```

Review the configuration in `.env` and then start the application:

```bash
docker compose up --build
```

Once the containers are running, access the application through the local URLs described below.

---

## Local Domains

The default local configuration uses two hostnames.

Add the following entries to the hosts file on the machine running the browser:

```text
127.0.0.1 cloud-cost.local
127.0.0.1 api-cloud-cost.local
```

If Docker is running on another machine on your local network, replace `127.0.0.1` with the LAN IP address of that Docker host.

## Environment Configuration

The application uses environment variables for local configuration.

The repository includes `.env.example` as a safe configuration template.

Create your local configuration with:

```bash
cp .env.example .env
```

### Available Parameters

| Parameter           | Description                                             | Default / Example             |
| ------------------- | ------------------------------------------------------- | ----------------------------- |
| `ENVIRONMENT`       | Identifies the application environment.                 | `development`                 |
| `FRONTEND_URL`      | URL used to access the frontend.                        | `http://cloud-cost.local`     |
| `BACKEND_URL`       | URL used to access the backend API.                     | `http://api-cloud-cost.local` |
| `POSTGRES_DB`       | PostgreSQL database name.                               | `cloud_cost`                  |
| `POSTGRES_USER`     | PostgreSQL username.                                    | `cloud_cost`                  |
| `POSTGRES_PASSWORD` | PostgreSQL password.                                    | Set your own local password   |
| `DATABASE_URL`      | PostgreSQL connection string used by the backend.       | See below                     |
| `MAX_UPLOAD_MB`     | Maximum upload size accepted by the application, in MB. | `500`                         |

### Example `.env`

```dotenv
ENVIRONMENT=development

FRONTEND_URL=http://cloud-cost.local
BACKEND_URL=http://api-cloud-cost.local

POSTGRES_DB=cloud_cost
POSTGRES_USER=cloud_cost
POSTGRES_PASSWORD=your_local_password

DATABASE_URL=postgresql://cloud_cost:your_local_password@database:5432/cloud_cost

MAX_UPLOAD_MB=500
```

### PostgreSQL Configuration

`POSTGRES_PASSWORD` and the password contained in `DATABASE_URL` must match.

For example:

```dotenv
POSTGRES_PASSWORD=my_local_password
```

The corresponding database URL is:

```dotenv
DATABASE_URL=postgresql://cloud_cost:my_local_password@database:5432/cloud_cost
```

If you change the PostgreSQL database name or username, update `DATABASE_URL` accordingly.

### Keep `.env Private

Do not commit your `.env` file to Git.

The repository's `.gitignore` excludes `.env` so that local configuration and passwords are not added to source control.

Use `.env.example` to document the required configuration without storing local secrets.

## AWS Cost and Usage Report

The application is designed around AWS Cost and Usage Report (CUR) data.

The basic workflow is:

```text
AWS CUR Data
     │
     ▼
Upload / Provide Billing Data
     │
     ▼
CUR Processing
     │
     ▼
Cost Analysis
     │
     ▼
Recommendation Rules
     │
     ▼
Cost Optimization Recommendations
```

The application analyzes the billing information available in the supplied data and applies its configured recommendation rules.

### Important

The application does **not** automatically make changes to your AWS environment as part of the basic analysis workflow.

Recommendations should be reviewed against your actual AWS architecture, workload requirements, commitments, and operational constraints before taking action.

---

## Recommendation Engine

The recommendation engine is rules-based and deterministic.

Each recommendation is generated when the available billing data satisfies the conditions defined by the corresponding analysis rule.

This approach provides several benefits:

* Predictable results
* Transparent analysis logic
* Repeatable recommendations
* Easier testing
* No dependency on an AI model for the core recommendation logic

The open-source edition intentionally exposes a focused set of cost-analysis capabilities.

Additional analysis capabilities may be developed separately as the project evolves.

This project is designed to support self-hosted analysis of AWS billing data.

```text
AWS Billing Data
      │
      ▼
Your Docker Environment
      │
      ├── Frontend

      └── PostgreSQL
```

Users should still review their own deployment configuration and infrastructure before processing sensitive billing information.

Do not commit:

* `.env` files
* AWS credentials
* API keys
* private certificates
* private customer data
* other sensitive configuration

to the repository.

## Production Direction

The open-source repository is primarily intended as a self-hosted/local deployment.

The same application architecture can also be deployed using managed infrastructure.

A planned production deployment pattern is:

```text
                    Cloudflare
                        │
             ┌──────────┴──────────┐
             ▼                     ▼
       Frontend                  Backend
        Vercel                 Cloud Run
                                   │
                                   ▼
                             Neon PostgreSQL
```

The production deployment can use environment variables for deployment-specific URLs and configuration rather than requiring application code changes.

The local Docker architecture and production deployment are intentionally kept separate so that the open-source project remains straightforward to run.
